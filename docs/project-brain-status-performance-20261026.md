## 2. 数据来源和计算口径

离线解析 r4 登记前的 `isolated-before-v221r4.dump`，SHA256 与备份登记的 `65f836ac82f60342cb9b7361613d292bda29eabd1b48762bc8edac201e10d41b` 一致。解析器读取 custom archive 的 TOC 和目标表，不启动数据库，不落盘原始 COPY 行或模型正文。

安全统计与可复现脚本位于 `secrets/brain-performance-audit-20261026/`。六个目标构建的调用 Token 合计均与 build 表一致；v203 的 2,048 次已结算调用、r3 的 367 次已结算调用与原 run-state/阶段报告一致。

- **构建壁钟**：build.created_at 至 completed_at，包括处理、队列、停顿及故障。
- **调用区间**：call.created_at 至 settled_at；这是预留至结算，包含发送前后、网络、网关和模型开销，不是纯推理时间。
- **调用 union**：合并重叠区间后的长度，表示至少一条已结算调用在途的时间。并发调用的 sum 不能当作壁钟。
- **阶段模型活动窗口**：该阶段首次预留至最后结算，不等于精确阶段起止。BrainUnit 没有 started/completed 时间字段。
- **无调用覆盖区间**：可能包含认证、文件/图处理、调度、记账或环境停顿，不能直接归因 CPU。unknown 不算成功延迟；另将其延长到构建终态作保守覆盖上界。

今日桌面 `docker ps` 未能连接默认 Docker named pipe；未进一步启动或切换环境，因此本次不能确认实时数据库和服务状态。备份是历史证据，不代表今日健康。

## 5. 代码已确认的开销来源

1. **重复认证与全仓校验。** 恢复 delivery 进入执行及创建 guard 会分别加载认证父链（`recovery.py:319-320,495-496`）。每次恢复 ledger refresh 会对各父 assert_current；收据匹配前后也有认证（`recovery_privacy.py:304,325`）。assert_current 经 reopen/freeze 重读 index、history、seal 和收据；freeze 为检测并发变化会两次读取收据 inventory（`:154-205,249-273`）。不能固定声称每次 check 都认证两遍：来源绑定会覆盖 discovery_check。
2. **每个 source_privacy/compile 重做整图工作。** 读取完整 facts、严格解析、摘要/MAC 验证（`brain_task.py:78-86,421`），validate 遍历所有 available 源文件并读字节计算 Git blob 哈希（`artifacts.py:225-236`），上下文命中前仍计算整 bundle 摘要（`brain_task.py:90-96`），来源认证还会比较全图 machine shape（`source_catalog.py:300-303`）。静态提取和 packets 有每进程内存缓存，并非每单元都重跑静态提取。
3. **两个执行槽与阶段屏障。** 本机 worker 写死 `--concurrency=2`（`compose.brain-local.yml:64`）。所有 source_privacy 完成后才 compile；所有 compile 完成后才汇总；每轮汇总全完成后再 planning（`brain_task.py:625-654`）。单元内隐私分包逐个 await，最终组装逐卡扫描。
4. **一个单元包含多次模型调用。** 编译/汇总除了语义生成，还包括必要输入和输出隐私扫描、格式修正及可能的分包；v203 已结算调用有 1,772 次隐私、276 次语义。调用次数占比和 Token 占比都不能当作耗时占比。
5. **普通增量尚未接回。** 这不会解释某一轮的异常空洞，但会显著增加未来每次代码更新的实际工作量。

前两项是代码确认的重复工作，且与 r3 零模型阶段的慢相符；**尚无 profiler 证明它们各占多少分钟**。环境空洞也不能全部归给认证。

Beat 的 15 秒是恢复兜底，正常任务完成后立即派发下一批，不是每单元固定等待 15 秒。模型 timeout 是保护上限，也不能拿来当平均耗时。现有 cost_plan 排除了隐私、输出、重试、汇总和组装，不能直接换算全流程 ETA。

## 6. 全流程大约多久

**尚无当前版本、同试点完整成功的端到端记录，不能给出已验证的完成时长。** 以下范围用于排期，不是实测 SLA：

- **稳定环境的冷首建：暂按 1.5～3 小时估计，低置信。** 依据是旧冷构建扣除最大空洞后约 64 分钟已完成全部编译及多数首轮汇总，再为剩余分层汇总、项目总览、最终隐私和产物留出余量。前提为相近项目规模、模型吞吐和两个执行槽；旧版本记录不能保证当前版本达到这个范围。
- **当前多父恢复：没有可信的“剩余几分钟”估计。** 已观察到 78 分钟才进入编译，模型调用节省不等于壁钟节省；应先量化认证开销，再计算 ETA。
- **现状下安排一次完整生产试点验收，宜预留半天窗口。** 这是应对未知后段和环境故障的排期余量，不表示正常生成必然需要半天，也不保证所有故障都能在窗口内解决。
- **日常小改动更新时间：目前不能承诺分钟级。** 须接回安全的普通增量，再根据真实变更包数和受影响汇总树测量。

以上只讨论知识产物生成。正式质量评估和 GitLab 发布另计；人工审批、CI 和合并等待没有可由本模块保证的固定时长。

## 7. 建议推进顺序

1. 补安全时序统计及原异常/发送阶段诊断：每单元拆出 queue_wait、load_recovery、parent_auth、receipt_inventory、facts_read_auth、source_blob_validate、catalog_auth、model_transport、budget_wait、complete_commit；只记固定标签、数量、字节与时间，不记正文、URL或异常消息。
2. 优先减少同一执行作用域内重复认证，并测量不可变快照/已认证图的安全复用。缓存绑定父 revision、manifest、DB 依赖及发现版本；晚响应、write-intent、隔离状态或材料变化必须失效，保留发送、结果接纳和封存处的围栏。
3. 接回 schema2 普通增量：只复用经过当前隐私策略、完整来源、依赖与内容兼容认证的结果，随后只重建受影响汇总。不能直接启用旧版公开图缓存。
4. 在稳定运行环境中完成一次受授权的完整 ready 构建，测真实阶段耗时和 p50/p95；先验证 manifest/ZIP/私有材料，再做冻结 50 题独立质量评估。
5. 之后评估增加并发和按依赖就绪调度汇总；先测 local_model 的吞吐及尾延迟，避免增加 worker 只增加排队、预算占用和失败率。单独完成真实发布与日常更新验收。

本次为状态与性能核查，没有实施上述优化，也没有新增真实执行授权。
