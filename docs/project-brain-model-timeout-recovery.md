## 已确认的问题

2026-10-20，2.0.2 对项目 480 的固定提交 `7d89860efe1113bcb1480bac2f1aaa9b1045bd8d` 执行了一次授权首建。隐私单元的一次请求在发送预留后抛出 `APITimeoutError`；任务重试后来完成了该单元，但原调用的响应和用量仍未收到。

2.0 的最终封存要求全部模型调用已结算、没有在途或未知预留。旧任务异常处理却允许上述请求重试，后续其他单元继续产生费用。新请求的成功响应属于新的调用 UUID，不能替代原请求，也不能使原调用自动结算。这是任务恢复策略与最终封存要求之间的工程缺口。

本例只有一次未知调用，客户端日志和任务日志各记录一次，不能统计为两次模型失败。未知调用预留 6,838 Token；全构建已结算 398,009 Token，总占用 404,847 Token。停止时隐私单元完成 143/165，其余 22 个因终止取消；没有语义请求、正式清单或 ZIP，不能给正式知识或 50 题评分。

请求创建时间为 `2026-10-20T09:00:23.506642Z`，首次错误日志为 `09:00:28.515159309Z`。约 5 秒与实际 SDK 默认的连接超时相符，但旧日志没有保留底层异常阶段，因此“可能发生在连接阶段”仍是推断。该请求窗口的容器 restart 为 0、OOM 为 false，所查 Windows 电源/重启事件无匹配；现有证据不支持归因于电脑关闭。它也不能证明模型能力不足。

## 2.0.3 的处理规则

`execute_brain_unit` 捕获异常后，仍按项目、构建、单元顺序取得锁并核验当前租约。先将未结算预留转为 unknown，再按 **build ID、unit ID、本次 lease token** 查询原调用：

| 状态 | 行为 |
|---|---|
| 本次调用已预留，异常退出后没有可结算响应 | 首次失败即终止，固定 `model_calls_incomplete`，不再 `self.retry` |
| 异常发生前没有调用预留 | 保留既有持久任务重试策略 |
| 调用已经结算，随后出现其他可重试错误 | 不误判为响应丢失，保留既有错误分类 |
| 正常扫描窗口续跑或预算暂时被占用 | 保留原检查点与等待机制，不消耗失败次数 |
| 其他单元或旧租约的 unknown | 不伪造成本次异常的响应丢失；最终完整调用门禁仍然拒绝 |

终止时保留已完成输出、扫描收据、HMAC 历史、已结算费用和未知预留；取消其他未完成租约。已经在途的并行请求仍可能产生费用，不能宣称全局即时零调用。新代码不把原费用清零，不以估算 0 结算，不删除未知记录，不降低最终隐私与封存门禁。

若服务实际取得原调用的迟到响应，原调用 ID、原租约和预留边界仍可用于正常结算；此能力保留。迟到结算可以修正费用，**不会自动恢复失败构建或把它变为 ready**。服务目前没有向网关查询丢失响应的机制。

## 安全的传输诊断

Brain 的 `metadata_errors=True` 日志增加 `transport_phase`。从异常自身及有界 cause/context 链读取具体 httpx 超时类型，最多访问 16 个不同异常，处理循环引用；值仅为 `connect`、`read`、`write`、`pool`、`unknown`。找不到类型时保留 unknown，不根据错误文本或耗时猜测。

日志不展开异常正文、URL、请求头、响应体或密钥。普通审查的既有日志路径、SDK 重试设置和超时参数保持原行为。没有新增配置或数据库迁移；当前 SDK 的 5 秒连接超时与 Brain 的 60 秒扫描调用上限均未调整。

## 尚未解决的边界与后续顺序

本次修复解决“已知无法封存却继续重试付费”的问题，不能修复真实网络可用性，也不能证明完整项目能生成成功。进程被强制结束、主机关闭等未经过异常处理的丢失响应，仍按原租约恢复流程处理；本次没有改写这一流程，最终封存仍会阻止未知调用发布。

后续应先根据新日志确认实际失败阶段，再决定是否调整连接窗口、连接建立方式或网关容量，不能将所有超时视为模型推理过慢。若需要继续支持响应丢失后的成功恢复，网关必须提供可靠的原请求身份、幂等发送及原响应/用量回查能力；单纯再次发送请求不构成恢复。未经网关契约验证，不实现虚假的“查询重试”或清理未知账目。

正式知识质量评估仍需成功构建：认证不可变清单和服务侧索引，独立对照固定源码，使用已冻结 50 题。ready 后快照会按现有流程清理，评估必须从独立 Git 缓存只读恢复相同 SHA 到评估私有临时区，不能依赖已清理的构建快照或改用分支最新源码。现有 2.0.2 专用评估门禁仍需在实际 ready 前据此适配。
